**For Ken.** Seven weeks unwatched (journal-033 on 2026-08-17 was the last

## 1. Verdict in one paragraph

The plumbing kept its promise: the service ran every night for seven weeks,
the dream pass fired on the store's own clock 68 times, the graph projection
is fresh, nothing is pending or unembedded, and yesterday's two fixes are
working. **The thesis did not get tested**, and it was not only the dead
outcome sweeper (journal-035) that starved it. The demand signal that
everything downstream of M3 rests on — `recall_count` — is being written
mostly by cron jobs reading their own bookkeeping, and a memory recalled
once can never be evicted. Meanwhile the knowledge tier is 78% of the store,
costs most of the extraction budget, and is recalled or browsed almost never.
The personal memory, which is the whole point, is small (a few dozen facts a
week), carries transient state and duplicates it should not, and recall
ranking is being skewed by the entity "ken". None of this is a crash. All of
it is the kind of quiet drift the August audit warned about: a zero that
records itself as "nothing needed doing".

## 2. The promise, and where it stands

BRIEF.md's falsifiable claim: Pip's tool-success-on-recall for the
**procedural** tier climbs over sessions the way gemma-forge's STIG curve did.

| What the curve needs | What the store has (2026-08-31 → 2026-10-20) |
|---|---|
| procedural recalls scored for outcome | 1,133 scored (most of them on 2026-10-20, the backlog) |
| recalls judged *followed* | 86, on **16 distinct memories** |
| negative outcomes | **1** |
| procedural memories whose confidence credit has moved | 0 with `failure_count > 0`; credit saturates at 1.0 after 3 successes |
| organic volume | 20–120 real turns a week; 5–30 procedural facts a week |

Three things, in order of weight:

1. **The sweeper was dead 2026-08-31 → 2026-10-20** (journal-035). Fixed and
   deployed yesterday; the first passes wrote 175 outcomes. That part is
   closed.
2. **There is no variance to learn from.** Pip's tool calls succeed almost
   every time (`tools 73/75 ok`, `85/87 ok` in the sweeper log). Followed +
   succeeded = +1.0, and `0.5 + credit` caps at 1.0, so every followed
   procedural memory sits at confidence 1.00 after three samples. The
   gemma-forge curve existed because STIG remediation *started* at 20%.
   A success rate that starts near 100% cannot produce a climb, and a store
   where nothing ever fails cannot discriminate good advice from bad. The
   claim as written needs a counterfactual (see R8).
3. **Volume.** Since 2026-08-17 the busiest week saw 160 turns, the median
   about 50. The thesis says "over sessions"; there have been few sessions.
   This is a usage fact, not a defect, but it bounds what any measurement
   can say before the new year.

Honest status: *mechanism shipped, loop live as of yesterday, curve
unmeasurable at this usage and this failure rate.* TASKS.md's "[~] THE CURVE"
is still the right mark.

## 3. What the system is actually doing

(78%), factual 1,558, procedural 952, preference 928, open_loop 587.

**Knowledge churn.** Thalamus feeds 500–1,000 knowledge facts a week

**Dream pass.** 68 reports in `/data/docker/gyrus/dream-reports/`, one a day,

**Reflective graph.** `entity_relations` = 7,541 rows, last computed

**Retrieval hygiene.** 0 retired memories recalled in the last 21 days.
Embedding leg answers in ~20 ms warm (measured from this host). Good.

## 4. Defects, ranked

### D1 — Cron jobs write the demand signal (HIGH)

The five most-recalled memories in the store, each at confidence 1.00:

| id | tier | recalls | from cron sessions | fact |
|---|---|---|---|---|
| 281 | procedural | 355 | 354 | Created cron job named pip-retention-maintenance … |
| 714 | factual | 354 | 351 | New cron job created: `pip-proactive-review` … |
| 645 | procedural | 354 | 351 | Created a cron job named pip-proactive-review … |
| 278 | procedural | 351 | 351 | cron.output_retention set to 96 |
| 953 | procedural | 333 | 333 | Cron job runs quietly when there is no new signal … |

85 live memories match cron bookkeeping; together they hold 1,884 recalls.
In the last 21 days, 1,295 of 3,370 retrieval rows came from `cron_*`
sessions (every scheduled run prefetches on the same prompt and hits the
same five memories). Cron *turns* are correctly refused as memory
(`worker._extract_turn`), but cron *recalls* count as demand:
`retrieval.log_retrievals` bumps `recall_count` for every caller, and
`consolidate._utility` turns that into confidence. The exact failure the M2
"done when" forbids — a recurring-but-useless memory outranking a
rare-but-valuable one — is the store's top five.

### D2 — One recall makes a memory immortal (HIGH)

`consolidate.py:150` evicts only when `recall_count == 0`. Any memory
recalled once, by anyone, for any reason, can never be retired by utility.
The four procedural memories the M3 harness *falsified* on 2026-08-16
(utility 0.215, journal-026) are still live at the bottom of last night's
report; journal-026's "demotion → eviction closes that over time" is false
by code. Combined with D1, cron bookkeeping is both top-ranked and
unevictable. The `log_retrievals` docstring promises the dream pass can see
"retrieved but never useful"; it cannot, because recall and usefulness are
the same counter.

### D3 — The entity "ken" skews the graph leg (MED)

`memory_entities` has 1,657 rows for `ken`; the IDF weight is
ln(18310/1657) ≈ 2.4, well above zero, so every query naming Ken pulls up to
40 arbitrary Ken-facts through the graph leg, and the agreement bonus
(`retrieval.py:216`) rewards them when the keyword leg also matches "ken".
Live probe: `Ken's usual bedtime` ranked "When Ken sends a concept…" and
"Ken expects the assistant to maintain its own environment…" above the exact
fact (id 23784, "Ken's usual bedtime is 10:30"); `what time does Ken go to
bed` did not surface it at all. The comment in the code names this exact
risk; the fix (a document-frequency cap) was not applied.

### D4 — Transient state stored as durable fact (MED)

Six live, mutually contradictory facts of the form "Ken's home is
approximately N miles from <coordinates>" (N = 1, 1, 2, 3, 5, 66; the
66-mile one at confidence 1.00). "Ken's phone is back home" has 200 recalls;
"phone location at 35.9006…" 141; "Ken is away in Norman, OK" 96. Eleven
such facts hold 791 recalls, all at confidence 1.00 — D1/D2 again, but fed
by `hearth` and `pipster` location chatter instead of cron. Since 2026-09-01
only 1 of 310 factual memories carries a `valid_until`; the extractor's
expiry class is effectively used only by open loops and knowledge.

### D5 — Personal-tier duplicates below the reconciler's floor (MED)

Among the 175 personal memories written since 2026-09-28: 5 pairs ≥ 0.93
(write-time dedupe missed them — likely the embedder-unavailable path from
the August audit's #9), 5 in the 0.90–0.93 band, 23 at 0.85–0.90, 44 at
0.80–0.85. Examples: the same Vitals correction-API bug stored as
factual 23787 *and* procedural 23792 (0.924, cross-tier, so the reconciler's
`b.tier = a.tier` join can never see it); "Ken's alcohol history during the
Panama stretch is unreliable" twice (24103 / 24114). Procedural is excluded
from the reconciler on purpose (its truth is outcome credit), but a
same-claim *fold* is not credit — 57 in-band procedural pairs are waiting.

### D6 — Open loops do not age (MED)

554 of 587 live open loops are older than 45 days. The most-recalled ones
are 2026-08-12/13 backfill loops at confidence 1.00: "Ken needs
confirmation whether the identified slide is the correct slide 2" (20
recalls), "Ken has not yet sent batch 3 pictures…" (16). The reconciler
closes a loop only on evidence; nothing closes a loop for being two months
old. Prompt v1.5's "open-loop durability exemption" lets in
"Find the current temperature in the office" and "Keep the master bedroom
lights off for the next hour".

### D7 — v1.5 mis-tiers one-shot commands as procedures (LOW–MED)

"Set the upstairs foyer main lights to 40 percent" → procedural. "Ken needs
to implement a cron module" → procedural (it is an open loop). "The
medication record is untouched" → factual. A re-tier spot check (TASKS audit
backlog) is overdue; the random procedural sample is roughly half genuine
procedures.

### D8 — The Vitals log is being copied into memory (LOW, judgment call)

126 live facts mention alcohol, medication or drinks: "Ken had one beer at
4:05", "Ken took one 25 mg capsule of hydroxyzine… on 10/13". These are
transactional records a system of record already holds, and they are the
most sensitive content in the store. The durable facts underneath ("Ken's
usual bedtime is 10:30", the sleep correlations) are worth keeping; the
per-drink ledger is not a memory.

### D9 — Every turn's recall is attributed to the *next* turn (MED)

Each captured turn has two prefetch events on the same query: one ~3 s
before the turn is written (the inline `prefetch`) and one ~0.3 s after it
(the provider's `queue_prefetch` warm-up, which re-fetches the question just
answered). `outcomes.link_retrievals` then claims every unlinked row in the
session for the next turn, so each turn is linked to its own leading recall
*and* the previous question's trailing recall. 161 of 254 turns in the last
21 days carry 10 rows for k = 5. Checked on 434 non-cron prefetches: every
one matches a captured turn, so turns are not being lost — but outcome
scoring judges the previous question's memories against this turn's tools,
`recall_count` is bumped twice, and the 3-sample credit guard can be met by
two turns.

### D10 — Cosmetic

Retired reason reads `low utility 0.33 < 0.33` (rounding in the message).
"Ken has unresolved tasks: Review current schema metrics…" sits in the
knowledge tier (GitHub journal re-ingest of Ken's own repos lands personal
content under `knowledge/github`).

## 7. Recommendations, in order

- **R1 (D1):** stop counting automated readers. In `api.prefetch`, skip
  `log_retrievals` (or at least the `recall_count` bump) when the session is
  a `cron_*` session; or have the provider not prefetch for cron. Then a
  one-off repair: recompute `recall_count` from non-cron retrievals.
- **R2 (D2):** make demand *earned*. Either count only followed/useful
  recalls toward utility, or replace `recall_count == 0` in the eviction
  guard with "not recalled in the last N days and no positive outcome", so
  demoted procedural memories can finally leave.
- **R3 (D3):** document-frequency cap in the graph leg: ignore entities
  present in more than ~2% of live memories ("ken", "pip", "hermes").
- **R4 (D4, D8):** extraction gate for transient state — location, "is
  away in", "is back home", per-event health records — either skip or
  force `expires: day`. Re-tier or retire the 11 live location facts.
- **R5 (D5):** let the reconciler fold same-claim pairs across tiers and
  include procedural in *folds* (not credit); consider a personal-tier
  floor of 0.85 with the LLM judge, capped per night.
- **R6 (D6):** open-loop ageing: default `expires` of ~45 days unless
  re-mentioned, and a one-off re-grade of the 554 stale loops.
- **R7 (knowledge):** decide what the knowledge tier is for. At 2% recall
  and 16 browses, either build the reader (`/v1/insights` in a page Ken
  will actually open) or throttle the sources, starting with the GitHub
  re-ingest.
- **R8 (the thesis):** add a counterfactual. Withhold procedural recall on
  1 in N eligible turns and compare retries/failures, or measure retries
  (tool failed then succeeded within the turn) as the outcome. Without
  variance there is no curve, however long it runs.
- **R9 (D9, C2):** drop the post-turn warm-up fetch in the provider (or send
  `log=0`), and stamp `followed_computed_at` on the no-tool-activity path so
  dead turns leave the sweeper's queue.
- **R10 (C1, C6, C8):** three small hardening fixes before the next long
  unattended stretch: wrap the consumer loop, page the graph cursor on
  `(updated_at, id)`, strip leading dashes from keyword tokens.
- **R11 (C3):** fuse per family — personal and knowledge candidate pools
  with a reserved share — so a 78% knowledge store cannot push personal
  memories out of the top-40 before weighting happens.
